# Пользователи

## Назначение функции

Управление доступом сотрудников к админке и Telegram/WebApp: просмотр пользователей, контроль статуса, роли и фактических прав.

Ключевая задача вкладки: быстро понять, кто имеет доступ, кто заблокирован или ожидает решения, и выполнить безопасное изменение статуса/роли.

## Что есть сейчас

- Вкладка называется `Пользователи`.
- Экран загружает `GET /api/users`.
- Доступ к API требует `users:manage`.
- На экране показана только таблица: имя, Telegram username, роль, статус.
- Ошибка загрузки показывается как общий `notice error`.
- Изменение пользователя в UI отсутствует, хотя API поддерживает `PATCH /api/users/:id`.
- API позволяет менять `status`; менять `role` можно только при наличии `roles:manage`.
- При изменении роли или статуса сервер отзывает активные сессии пользователя.
- Сервер пишет audit-событие `user/update`.

## UI controls and data chain

- UI: `UsersView` в `src/client/src/main.tsx`.
- Клиентский state:
  - `users: User[]`;
  - `message: string`.
- Загрузка: `useEffect` -> `client.request<User[]>("/api/users")`.
- Отображение: `DataTable`.
- Текущие поля строки:
  - `Имя`: `firstName + lastName`;
  - `Telegram`: `username`;
  - `Роль`: `role`;
  - `Статус`: `status`.
- Доступные в модели поля, которые UI не использует:
  - `id`;
  - `telegramUserId`;
  - `permissions`.
- Доступный, но не подключенный action:
  - `PATCH /api/users/:id` с `status` и/или `role`.

## UX/UI огрехи относительно сути функции

- Вкладка называется управлением пользователями, но фактически это read-only список.
- Нет поиска по имени, username, Telegram ID или внутреннему ID.
- Нет фильтров по статусу и роли.
- Нет счетчиков: активные, pending, blocked, rejected, archived.
- Не видно Telegram ID, из-за чего сложнее сверять пользователя с Telegram-аккаунтом.
- Не видно фактических permissions, хотя именно они определяют доступ.
- Нет действий для approve/block/reject/archive/reactivate.
- Нет изменения роли, хотя серверный контракт это поддерживает.
- Нет объяснения ограничения: роль может менять только пользователь с `roles:manage`.
- Нет подтверждения опасных действий: блокировка, архивирование, смена роли.
- Нет информации, что смена статуса/роли отзовет активные сессии.
- Нет inline-состояний загрузки, обновления и сохранения.
- Нет построчной ошибки при неудачном обновлении.
- Статусы и роли показаны техническими значениями без визуального приоритета.
- Нет пустого состояния для отсутствия пользователей.

## Как должно быть реализовано в новом дизайне

- Сделать вкладку полноценным экраном управления доступом, а не только справочником.
- Верх экрана: счетчики по статусам и быстрый фильтр `Все / Ожидают / Активные / Заблокированные / Архив`.
- Основная таблица должна поддерживать поиск, фильтр по роли, фильтр по статусу и сортировку.
- В строке пользователя показать:
  - ФИО;
  - username;
  - Telegram ID;
  - роль;
  - статус;
  - краткий набор прав;
  - доступные действия.
- Статусы показывать бейджами с понятным русским текстом.
- Роли показывать как `Продавец`, `Админ`, `Суперадмин`, но хранить связь с enum.
- Действия:
  - активировать pending;
  - заблокировать active;
  - отклонить pending;
  - вернуть blocked в active;
  - архивировать неактуального пользователя;
  - изменить роль при наличии `roles:manage`.
- Для смены статуса/роли нужен confirm-dialog с явным текстом о ревокации сессий.
- После успешного изменения обновлять строку без потери фильтров.
- После ошибки показывать причину рядом с действием.
- Если текущему оператору недоступно `roles:manage`, control смены роли должен быть disabled с короткой причиной.
- В деталях пользователя показать permissions списком и последние audit-события по `entity=user`, если новый API это отдаст.
