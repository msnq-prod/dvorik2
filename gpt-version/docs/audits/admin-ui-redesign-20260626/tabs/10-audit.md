# Аудит

## Назначение функции

Просмотр технического журнала действий и управление резервными копиями состояния приложения.

Ключевая задача вкладки: быстро ответить, кто, когда и что изменил, а также безопасно создать или восстановить backup.

## Что есть сейчас

- Вкладка называется `Аудит`.
- Экран одновременно содержит два блока: `Backups` и `Аудит`.
- При открытии загружаются `GET /api/audit` и `GET /api/backups`.
- Доступ к audit и backups требует `techlog:read`.
- `GET /api/audit` возвращает последние 100 записей из `db.audit`.
- Новые audit-записи добавляются через `unshift`, то есть сверху самые свежие.
- Таблица audit показывает только: время, сущность, действие, автор.
- Доступные поля `id`, `entityId`, `changes` не отображаются.
- Создание backup доступно кнопкой `Создать backup`.
- Восстановление доступно отдельными кнопками только для первых трех backup-файлов.
- Backup-таблица показывает файл, размер, дату создания.
- Restore вызывает `POST /api/backups/:name/restore`.
- Создание и восстановление backup пишутся в audit как `backup/create` и `backup/restore`.

## UI controls and data chain

- UI: `Audit` в `src/client/src/main.tsx`.
- Клиентский state:
  - `audit: AuditEntry[]`;
  - `backups: any[]`;
  - `message: string`.
- Загрузка audit: `client.request<AuditEntry[]>("/api/audit")`.
- Загрузка backups: `client.request<any[]>("/api/backups")`.
- Создание backup:
  - кнопка `Создать backup`;
  - `POST /api/backups`;
  - повторная загрузка backups.
- Восстановление backup:
  - кнопки для `backups.slice(0, 3)`;
  - `POST /api/backups/{name}/restore`;
  - повторная загрузка backups.
- Audit table:
  - `createdAt` -> локализованное время;
  - `entity`;
  - `action`;
  - `actorId`.
- Backup table:
  - `name`;
  - `bytes`;
  - `createdAt`.

## UX/UI огрехи относительно сути функции

- Audit и backups смешаны в одной вкладке без ясной иерархии.
- Журнал не показывает `entityId`, поэтому запись часто нельзя связать с конкретным объектом.
- Не отображается `changes`, хотя это главное содержимое audit-события.
- `actorId` показан техническим ID без имени пользователя.
- Нет фильтров по дате, автору, сущности и действию.
- Нет поиска по `entityId`, `actorId`, `changes`.
- Нет раскрытия строки с деталями события.
- Нет пагинации или lazy-load; сервер отдает только первые 100 записей.
- Нет явного текста, что показаны только последние 100 событий.
- Нет экспорта журнала.
- Нет защиты от случайного restore.
- Restore доступен только для первых трех backup-файлов, остальные видны, но без действия.
- Нет статусов выполнения для create/restore.
- Нет отдельного success/error результата для backup-операций.
- Размер backup показан в байтах без человекочитаемого формата.
- Нет проверки последствий restore: восстановление может резко изменить все состояние приложения.
- Ошибка любой загрузки превращает весь экран в один общий error state.

## Как должно быть реализовано в новом дизайне

- Разделить экран на две смысловые зоны: `Журнал действий` и `Резервные копии`.
- Audit должен быть основной частью вкладки; backup-блок — отдельная управляемая секция.
- Для audit добавить toolbar:
  - период;
  - автор;
  - сущность;
  - действие;
  - поиск;
  - обновить.
- Таблица audit должна показывать:
  - время;
  - автора с именем, если возможно;
  - сущность;
  - ID объекта;
  - действие;
  - краткое описание изменений;
  - кнопку раскрытия деталей.
- Детали audit-события должны показывать полный `changes` в читаемом JSON-viewer.
- Если имена пользователей недоступны в текущем API, новый дизайн должен предусмотреть join с users или отдельный resolver.
- Обязательно показать ограничение текущего API: `последние 100 событий`.
- Backup-секция должна показывать все backup-файлы с действием restore в строке.
- Restore должен требовать confirm-dialog с названием файла и предупреждением о восстановлении состояния.
- Создание backup должно иметь pending state и success message.
- Restore должен иметь pending state, success/error message и последующее обновление списка.
- Размер backup показывать в KB/MB.
- Для операций backup использовать отдельные ошибки, не ломая audit-таблицу.

## Самостоятельная вкладка: состав экрана

- Header:
  - название `Аудит`;
  - подпись `Последние события и резервные копии`;
  - действие `Обновить`.
- Top metrics:
  - число показанных событий;
  - последнее событие;
  - число backup-файлов;
  - дата последнего backup.
- Section `Журнал действий`:
  - toolbar фильтров;
  - таблица событий;
  - expandable row с `changes`;
  - empty state;
  - loading state.
- Audit columns:
  - время;
  - автор;
  - сущность;
  - объект;
  - действие;
  - изменения;
  - детали.
- Section `Резервные копии`:
  - кнопка `Создать backup`;
  - таблица backup-файлов;
  - action restore в каждой строке;
  - confirm-dialog restore.
- Backup columns:
  - файл;
  - создан;
  - размер;
  - действия.
- States:
  - forbidden для отсутствия `techlog:read`;
  - independent loading для audit;
  - independent loading для backups;
  - create backup pending;
  - restore pending;
  - operation-level error.

## Acceptance checklist

- [ ] Вкладка загружает audit через `GET /api/audit`.
- [ ] Вкладка загружает backups через `GET /api/backups`.
- [ ] При отсутствии `techlog:read` показан понятный forbidden state.
- [ ] Audit-таблица показывает время, автора, сущность, ID объекта, действие и краткие изменения.
- [ ] Поле `changes` доступно в раскрытии строки.
- [ ] Есть фильтры по периоду, автору, сущности и действию.
- [ ] Есть поиск по `actorId`, `entity`, `entityId`, `action`, `changes`.
- [ ] UI явно сообщает, что текущий API возвращает последние 100 событий.
- [ ] Backup-файлы показываются все, а не только первые три для restore.
- [ ] Размер backup отображается в человекочитаемом формате.
- [ ] Создание backup вызывает `POST /api/backups`.
- [ ] Restore вызывает `POST /api/backups/:name/restore`.
- [ ] Restore требует подтверждения с названием backup-файла.
- [ ] Ошибка audit не скрывает backup-секцию, если backups загрузились.
- [ ] Ошибка backups не скрывает audit-секцию, если audit загрузился.
- [ ] После create/restore список backups обновляется.
