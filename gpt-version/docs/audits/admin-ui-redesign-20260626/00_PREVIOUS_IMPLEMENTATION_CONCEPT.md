# Обобщенная концепция прошлой реализации

## Старое меню и роль в продукте

Старая админка была не складским инструментом, а CRM/маркетинг-панелью для Telegram-программы лояльности.

Меню делилось на три смысловые группы:

- `Управление`: главная, пользователи, шаблоны скидок, кассиры.
- `Маркетинг`: рассылки, реферальные кампании.
- `Система`: логи и отчеты, настройки.

Навигация была построена вокруг ролей `owner`, `marketing`, `readonly`. Видимость пунктов задавалась прямо в конфигурации меню. По факту роль была заглушкой `owner`, но сама идея ролевого меню уже была заложена.

Роль меню в продукте: быстро развести оператора по CRM-сценариям, где главные сущности - пользователи Telegram, скидки, кассиры, рассылки и системные настройки.

В текущей `gpt-version` меню уже другое по предметной области: главная, товары, склад, инвентаризация, маркировки, импорт, дубли, график, пользователи, аудит. Это ближе к складской админке, но пока остается плоским списком без группировки по рабочим контурам.

## Как был устроен app shell

Старая реализация использовала готовый shell:

- `QueryClientProvider` для React Query.
- `ThemeProvider` и `ThemeToggle` для светлой/темной темы.
- `TooltipProvider` и `Toaster` как глобальные UI-сервисы.
- `SidebarProvider`, `AppSidebar`, `SidebarTrigger` для адаптивного сайдбара.
- `wouter`-роутинг через `Switch` и `Route`.
- Основная область: фиксированный экран `h-screen`, слева сайдбар, сверху компактный header, ниже прокручиваемый `main`.

Сайдбар был компонентным: бренд сверху, группы меню внутри, footer с выходом. Активное состояние определялось текущим URL. Пункты были ссылками, а не локальным состоянием.

Текущая `gpt-version` устроена проще:

- весь frontend собран в одном `main.tsx`;
- активный раздел хранится в локальном `view`;
- роутинга нет;
- сайдбар - статичный список кнопок;
- topbar содержит заголовок текущего раздела, пользователя, режим авторизации и переключатель темы;
- shell задан CSS-grid: `260px + 1fr`;
- мобильная версия превращает сайдбар в верхнюю сетку кнопок.

Для складской админки текущий shell уже отражает нужные домены, но старый shell был сильнее как архитектурный каркас: роуты, провайдеры, группировка, footer, collapse-trigger, UI-инфраструктура.

## Что уже полезно сохранить

- Левый persistent sidebar как основную навигацию для desktop.
- Группировку меню по смысловым блокам, а не один длинный список.
- Конфигурационный формат меню: title, url/view, icon, roles/permissions.
- Ролевую видимость пунктов, но перенести ее с CRM-ролей на текущие `Role`/`Permission`.
- Активное состояние пункта меню.
- Бренд-блок сверху.
- Footer-зону для выхода, профиля, статуса сессии или служебных действий.
- Глобальные провайдеры shell: тема, tooltip, toast/notice.
- Компактный topbar с глобальными действиями.
- Адаптивное поведение: desktop sidebar, tablet/mobile collapsed или верхняя навигация.
- Сухой admin-dashboard стиль: плотные таблицы, формы, фильтры, статусы, минимум декоративности.

Из текущей `gpt-version` нужно сохранить предметную структуру:

- товары и идентификаторы;
- складские операции;
- остатки и локации;
- инвентаризация;
- маркировки и печать;
- импорт поставок;
- объединение дублей;
- график смен;
- пользователи, роли, аудит, backup.

## Что не соответствует новой складской админке

Старая реализация не подходит по предметной модели:

- центр продукта - Telegram-лояльность, а не склад;
- нет товаров, складов, остатков, перемещений, инвентаризации и маркировок;
- меню ориентировано на маркетолога и владельца, а не на складского оператора, администратора и продавца;
- кассиры в старом смысле связаны с проверкой скидок, а не с рабочими сменами и операциями магазина;
- отчеты и логи не покрывают audit trail складских движений;
- настройки не разделены на складские справочники, роли, импорт, печать и системное обслуживание.

Старая UX-логика тоже требует пересборки:

- карточки скидок и broadcast builder не являются базовыми паттернами для склада;
- CRM-таблицы пользователей не должны диктовать структуру товарных и складских экранов;
- маркетинговые группы меню нельзя просто переименовать в складские;
- роль `readonly` недостаточна: в новой модели нужны permission-based сценарии вроде `products:read`, `stock:move`, `inventory:write`, `labels:print`, `users:manage`.

Текущая `gpt-version` уже ближе к новой админке, но ее меню пока слишком плоское и не показывает иерархию складских процессов.

## Требования к новому мега-меню/сайдбару

Новое меню должно быть складским рабочим инструментом, а не CRM-навигацией.

Базовые группы:

- `Операции`: главная, склад, инвентаризация, маркировки.
- `Каталог`: товары, дубли, импорт.
- `Люди`: график, пользователи, роли/доступы.
- `Контроль`: аудит, backup, журнал операций, системные события.
- `Настройки`: локации, шаблоны печати, импортные правила, системные параметры.

Пункты меню должны строиться из единой конфигурации:

- стабильный ключ;
- текст;
- иконка;
- route или view;
- краткое описание для mega-menu;
- required permissions;
- optional badge/count;
- порядок внутри группы.

Мега-меню должно помогать быстро выбрать сценарий, а не просто показывать список страниц. Для каждого крупного раздела нужны быстрые действия:

- `Товары`: найти товар, создать товар, открыть архив, проверить дубли.
- `Склад`: провести приход, перемещение, списание, открыть остатки.
- `Инвентаризация`: создать snapshot, продолжить проверку, применить корректировки.
- `Маркировки`: собрать этикетки, скачать PDF, повторить печать.
- `Импорт`: загрузить файл, открыть предпросмотр, отменить примененный импорт.
- `График`: создать смену, неделя, месяц, заявки на обмен.
- `Контроль`: аудит, backup, восстановление, журнал ошибок.

Требования к поведению:

- фильтровать пункты по `permissions`, а не только по роли;
- не показывать недоступные действия обычному продавцу;
- поддержать collapsed sidebar на desktop;
- на mobile использовать компактный режим без потери основных операций;
- сохранять активную группу и активный пункт;
- показывать счетчики для низких остатков, непримененных импортов, pending-заявок, ошибок аудита;
- оставить topbar для текущего раздела, пользователя, темы и режима авторизации;
- не смешивать маркетинговые сущности старой CRM с новой складской моделью.

Минимальная целевая структура для `gpt-version`:

- `Главная` - обзор склада, низкие остатки, последние движения.
- `Товары` - каталог, поиск, карточки, идентификаторы, архив.
- `Склад` - остатки, приход, перемещение, списание, журнал операций.
- `Инвентаризация` - snapshot, ввод факта, дельты, применение корректировок.
- `Маркировки` - шаблоны, предпросмотр, PDF, журнал печати.
- `Импорт` - preview, commit, undo, история файлов.
- `Дубли` - preview merge, commit, undo.
- `График` - смены, заявки, управление расписанием.
- `Пользователи` - сотрудники, статусы, роли, доступы.
- `Контроль` - аудит, backup, восстановление, технический журнал.
