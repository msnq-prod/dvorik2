# Целевые workflows

## WF-01. Первый вход

1. Пользователь открывает бота.
2. Бот проверяет наличие active user.
3. Если доступа нет, запускается заявка: имя → фамилия → отправка.
4. Администратор получает уведомление.
5. При одобрении пользователь получает кнопку открытия WebApp.
6. Backend проверяет Telegram init data и выдаёт сессию.

Ошибки: просроченная подпись, blocked user, повторная заявка, отказ с причиной.

## WF-02. Standalone-вход

1. Авторизованный пользователь запрашивает ссылку через бота.
2. Backend создаёт одноразовый short-lived token.
3. Browser обменивает токен на сессию.
4. Токен сразу инвалидируется.

Запрещено хранить постоянный токен в URL.

## WF-03. Поиск и открытие товара

1. Пользователь вводит текст либо сканирует штрихкод.
2. Поиск учитывает названия, локальное имя, все артикулы и штрихкоды.
3. Пользователь открывает товар.
4. Карточка показывает фото, названия, идентификаторы, единицу и остатки по локациям.
5. Доступные действия вычисляются backend по permissions.

## WF-04. Перемещение

1. Выбрать/отсканировать товар.
2. Backend возвращает локации с положительным остатком.
3. Один источник выбирается автоматически; несколько требуют выбора.
4. Выбрать назначение.
5. Ввести количество либо нажать быстрое `1`.
6. UI показывает итог: откуда, куда, количество.
7. Backend атомарно применяет команду.
8. UI показывает новый остаток и ID операции.

Повторный запрос не должен удваивать движение.

## WF-05. Списание в зал

Как WF-04, но назначение — бизнес-действие `write_off_to_hall`. Остаток назначения не создаётся.

## WF-06. Инвентаризация

1. Выбрать локацию.
2. Загрузить snapshot товаров и versions.
3. Вводить фактические количества.
4. Для каждой позиции показывать разницу.
5. Перед применением проверить отсутствие конфликтующего изменения.
6. При конфликте потребовать обновление и повторное подтверждение.
7. Применить корректировки атомарно в допустимом объёме.

OPEN: блокировка всей локации или optimistic concurrency по строкам.

## WF-07. Импорт поставки

1. Загрузить файл.
2. Проверить формат, размер и SHA-256.
3. Определить поставщика и сохранённый mapping.
4. При необходимости сопоставить колонки.
5. Нормализовать строки.
6. Показать новые товары, точные совпадения, неоднозначные строки и ошибки.
7. Пользователь разрешает неоднозначности.
8. Подтвердить итоговый diff.
9. Backend применяет поставку одной транзакцией.
10. Показать неизменяемый результат.

## WF-08. Откат поставки

Текущего решения недостаточно. Требование откатывать поставку после последующих движений конфликтует с обычным balance-based учётом.

Допустимые направления:

- партии остатка и provenance;
- компенсирующая операция с детальным анализом последующих движений;
- запрет полного отката и отдельная корректировка.

Агент не выбирает вариант самостоятельно.

## WF-09. Объединение дублей

1. Выбрать две карточки.
2. Получить diff полей и связей.
3. Выбрать итоговые значения.
4. Показать перенос остатков, identifiers и фото.
5. Подтвердить.
6. Применить одной транзакцией.
7. Вторую карточку пометить merged/deleted.
8. Сохранить snapshot для undo.

## WF-10. Печать маркировок

1. Выбрать товары.
2. Настроить геометрию этикетки и поля.
3. Получить live preview A4.
4. Проверить переполнение каждой этикетки.
5. Сформировать PDF.

Инструмент Stones используется как технический reference, но модель данных и поля Dvorik проектируются отдельно.

## WF-11. Обмен сменами

1. Сотрудник выбирает свою смену.
2. Выбирает коллегу.
3. Коллега принимает или отклоняет.
4. При принятии назначения меняются атомарно.
5. Оба сотрудника и администратор получают уведомление.

## WF-12. Отмена складской операции

1. Администратор находит операцию.
2. Backend проверяет permission, состояние и отсутствие предыдущей отмены.
3. UI показывает компенсирующее действие.
4. Создаётся reversal operation.
5. Оригинальная запись остаётся неизменной.
