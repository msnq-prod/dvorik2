# Три варианта документации для AI-агентов

## Вариант 1. Единый handbook

### Структура

- Один подробный `AGENTS.md`.
- Один `PROJECT_SPEC.md`.
- Один `TASKS.md`.

### Плюсы

- Быстро создать.
- Агенту просто найти точку входа.
- Подходит для короткого прототипа и одного разработчика.

### Минусы

- Файл быстро становится огромным.
- Одни и те же факты начинают дублироваться.
- Агент читает много нерелевантного контекста.
- Высокий риск устаревших инструкций.

### Риск ошибок

Средний/высокий. Текущий большой `AGENTS.md` уже демонстрирует этот недостаток.

## Вариант 2. Модульная каноническая документация

### Структура

- Короткий root `AGENTS.md` только с правилами и маршрутизацией.
- `docs/product/` — требования и роли.
- `docs/domains/` — товары, склад, поставки, расписание.
- `docs/workflows/` — пользовательские процессы.
- `docs/adr/` — принятые архитектурные решения.
- `docs/tasks/` — планы и progress конкретных изменений.

### Плюсы

- Агент загружает только нужный домен.
- Есть явные источники истины.
- Удобно обновлять по частям.
- Хорошо работает с несколькими параллельными агентами.

### Минусы

- Требует дисциплины ссылок и владельцев документов.
- Документы всё ещё могут расходиться с кодом.

### Риск ошибок

Низкий при обязательном обновлении docs в каждом PR.

## Вариант 3. Executable specification

### Структура

- OpenAPI/JSON Schema для API.
- Versioned DB migrations.
- Permission matrix в YAML/JSON.
- State machines в машинно-читаемом виде.
- Contract и acceptance tests как обязательная часть спецификации.
- Документация генерируется из контрактов.

### Плюсы

- Максимально снижает пространство для интерпретации.
- Несоответствие кода обнаруживается CI.
- Агент может проверять решение автоматически.
- Лучше всего защищает складские данные.

### Минусы

- Самая высокая начальная стоимость.
- Требует выбранного стека и CI.
- Не заменяет продуктовые тексты и UX-сценарии.

### Риск ошибок

Минимальный для контрактов и инвариантов.

## Рекомендация

Использовать **вариант 2 как основу** и добавить из варианта 3:

- OpenAPI;
- versioned migrations;
- permission matrix;
- state machines поставки и обмена сменами;
- contract tests;
- acceptance tests критических складских операций.

Это даёт понятный контекст агентам без чрезмерной инфраструктуры.

## Рекомендуемый root `AGENTS.md`

Root-файл должен занимать примерно 80–150 строк и содержать только:

1. Что это за проект.
2. Иерархию источников истины.
3. Порядок чтения документов.
4. Команды setup/test/lint/migrate.
5. Критические инварианты.
6. Запрещённые действия.
7. Definition of Done.

Описание каждой функции должно находиться в доменном документе, а не дублироваться в `AGENTS.md`.
