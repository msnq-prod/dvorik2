# Документация нового Dvorik WebApp

Этот каталог описывает целевой продукт. Старый Python-бот и Flask CRM используются как источник существующих бизнес-сценариев, но не как целевая архитектура.

## Порядок чтения для AI-агента

1. `01_PRODUCT_BRIEF.md` — что строим и для кого.
2. `02_FEATURE_CATALOG.md` — полный состав функций и границы MVP.
3. `03_DOMAIN_MODEL.md` — сущности, инварианты и права.
4. `04_WORKFLOWS.md` — ключевые пользовательские процессы.
5. `05_TARGET_ARCHITECTURE.md` — архитектурные ограничения.
6. `06_DELIVERY_PLAN.md` — этапы разработки и критерии готовности.
7. `07_OPEN_DECISIONS.md` — вопросы, которые нельзя решать агенту самостоятельно.
8. `08_AI_DOCUMENTATION_OPTIONS.md` — варианты организации документации.
9. `09_LEGACY_REFERENCE_MAP.md` — где искать старое поведение.
10. `10_ACCEPTANCE_MATRIX.md` — проверяемые критерии функций.
11. `00_DISCOVERY_QUESTIONS.md` — исходные ответы владельца продукта.

## Иерархия источников истины

При конфликте использовать порядок:

1. Принятые ADR/решения и `07_OPEN_DECISIONS.md`.
2. Целевая документация из этого каталога.
3. Автоматические контракты: схема БД, API-схема, permission matrix, тесты.
4. Текущий код старого приложения.
5. Старые `README.md`, `AGENTS.md` и аудиты.

Старый код показывает, **как работало**, но не определяет, **как должно быть построено**.

## Статусы требований

- `CONFIRMED` — подтверждено ответами владельца.
- `INFERRED` — выведено из старого поведения; требует проверки.
- `OPEN` — решение не принято.
- `DEFERRED` — не входит в ближайший этап.

## Запреты для агентов

- Не переносить прямой SQL из handlers/blueprints в новый API.
- Не считать артикул уникальным идентификатором товара.
- Не менять складской остаток без атомарной доменной операции и записи в журнал.
- Не реализовывать откат поставки простым вычитанием текущего остатка.
- Не принимать решения из `07_OPEN_DECISIONS.md` без владельца продукта.
- Не копировать старый UI один в один.
- Не добавлять функцию без критериев приёмки и проверки прав.
