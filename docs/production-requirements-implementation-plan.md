# План доработок production-версии Dvorik

Дата: 2026-07-20  
Основание: `production-requirements-discovery.md`  
Целевой продукт: `gpt-version`  
Статус: подход и последовательность работ; реализация не начата

## 1. Выбранный подход

### Решение

Дорабатывать `gpt-version` эволюционно как модульный монолит. Полную перепись
проекта не выполнять.

Работы вести в следующем порядке:

1. закрыть решения, влияющие на данные и права;
2. изменить доменную модель и схему БД;
3. вводить функции законченными вертикальными срезами;
4. только после этого собирать финансовые отчёты и production-релиз.

`recovered-dvorik` остаётся только справочным источником. Новую логику нельзя
добавлять в legacy `AppState`, dev-совместимость или отключённые production-
маршруты.

### Почему этот подход

- В `gpt-version` уже есть пригодная основа: SQLite-миграции, repositories/UoW,
  идемпотентность, аудит, outbox, защищённые сессии, роли, release-проверки и
  резервное копирование.
- Новые требования меняют не только интерфейсы, но и смысл товара, остатка,
  поставки, расхода и выручки. Их нельзя безопасно добавить поверх текущей
  универсальной модели `товар + количество + локация`.
- Импорт и merge уже изолированы от первого production-контура. Их рациональнее
  заново подключить к новой модели, чем расширять старые временные пути.
- Вертикальные срезы позволяют принимать каждый контур отдельно и не ждать
  завершения всей системы для проверки продавцами.

### Что сохраняется, меняется и исключается

| Решение | Область |
| --- | --- |
| Сохранить и расширять | TypeScript-приложение, SQLite, миграции, транзакции, audit, idempotency, outbox, auth/session, responsive WebApp, базовый календарь |
| Перестроить | карточка товара, остатки, локации, инвентаризация, импорт, merge, отчёты и матрица прав |
| Добавить | группы и история цен, пачки, партии/FIFO, Saby, расходы, зарплата, налоги, финансовые периоды, оборачиваемость |
| Не переносить | данные старой системы, legacy runtime, ручные продажи штучных товаров, старый недельный пересчёт штучных товаров |

## 2. Архитектурная модель

### 2.1. Источники истины

| Данные | Канонический источник |
| --- | --- |
| Карточка товара | каталог Dvorik |
| Тип товара и масса пачки | карточка товара Dvorik |
| Общий складской остаток | неизменяемые складские операции и текущая агрегированная проекция |
| Размещение по полкам | отдельная проекция размещения, не самостоятельный склад |
| Себестоимость | партии поставок и FIFO-распределения |
| Фактический расход весового товара | закрытая инвентаризация |
| Оперативный расход весового товара | переносы со склада в зал до закрытия периода |
| Продажи и возвраты штучного товара | завершённые фискальные операции Saby |
| Фактическая общая выручка | Saby |
| Оценка выручки отдельных весовых товаров | отдельный расчётный контур Dvorik |
| График смен | модуль расписания Dvorik |
| Финансовый результат | зафиксированные продажи, FIFO, зарплата, расходы и налоговые правила Dvorik |

### 2.2. Остаток и локации

Нужно разделить два понятия:

- **общий остаток товара на складе** — учётное наличие;
- **размещение** — сколько целых пачек или единиц лежит на каждой полке.

Локация не получает самостоятельный финансовый или складской контур. Размещение
является оперативной подсказкой, а не источником фактического остатка. Оно не
обязано автоматически сходиться с общим остатком после инвентаризации.

Инвентаризационный расход применяется к общему остатку без выбора полки и без
корректировки размещений. Это не «неизвестное расхождение», а фактический расход
товара за период. При выключенных полках новые поставки временно размещаются в
общей локации «Склад» и распределяются после повторного включения.

Текущую сущность `locations` нельзя одновременно использовать для полок,
рабочего графика и точки Saby. В целевой модели это разные понятия:

- `stock_locations` — полки и отсеки;
- `retail_point` — единственная торговая точка и её связь с Saby;
- расписание привязано к торговой точке, а не к складской полке.

Это позволяет:

- проводить инвентаризацию без пересчёта каждой полки;
- выключать и включать полки без потери учётного остатка;
- хранить приблизительное размещение отдельно от фактического наличия;
- учитывать расход периода без искусственного выбора полки-источника.

### 2.3. Единицы учёта

- Весовой товар хранится в целых заводских пачках.
- В карточке весового товара обязательна точная масса пачки в граммах.
- Килограммы являются вычисляемым значением для отчётов и цены, но не единицей
  складского ввода.
- Штучный товар хранится только целым числом единиц.
- Одинаковое название с разной массой пачки создаёт разные карточки.
- Денежные значения хранятся в копейках, масса — в граммах, количество пачек и
  штук — целыми числами.

### 2.4. Неизменяемый журнал операций

Любое изменение состояния оформляется отдельным событием:

- поставка;
- размещение и перемещение между полками;
- перенос одной пачки весового товара в зал;
- продажа и возврат штучного товара из Saby;
- брак;
- закрытие инвентаризации;
- откат поставки;
- административная корректировка;
- merge и undo merge.

История не переписывается. Отмена создаёт компенсирующую операцию. Audit,
идемпотентность и outbox фиксируются в одной транзакции с бизнес-операцией.

### 2.5. Разделение финансовых фактов

Нельзя смешивать в одном показателе:

1. фактическую кассовую выручку;
2. расчётную выручку отдельного весового товара;
3. прогноз даты признания последнего весового списания.

Каждый показатель хранится с типом, источником, периодом и использованной
исторической ценой. Итоговый отчёт использует Saby как главный факт, а оценку
весовых товаров показывает отдельно и не распределяет общую кассовую выручку
по вымышленным пропорциям.

### 2.6. Границы модулей

Рекомендуемые модули внутри текущего backend:

- identity и access;
- catalog и product groups;
- stock и placements;
- supplies, lots и FIFO;
- inventory periods;
- Saby integration и external mappings;
- revenue recognition;
- schedule и payroll;
- expenses, taxes и financial periods;
- reports и analytics;
- notifications и operations.

WebApp, Telegram и фоновые задачи вызывают одни application services. Бизнес-
правила не дублируются в transport-обработчиках.

### 2.7. Явные нецели

- Перенос каталога, остатков, пользователей и истории legacy.
- Регламентированный бухгалтерский или налоговый учёт и отправка данных в ФНС.
- Создание новых товаров в Saby из Dvorik в первом приоритете.
- Распределение общей кассовой выручки «Сладостей» по отдельным товарам.
- Экспорт графиков в PDF/Excel/CSV и сравнение нескольких товаров на одном
  графике.
- Постоянный отдельный test-контур. Проверки релиза выполняются в изолированном
  временном окружении и на копии БД.

### Обязательная спецификация перед payroll-модулем

До реализации расчёта владелец отдельно фиксирует: оклад как начисленную сумму
или сумму к выплате, формулы НДФЛ и взносов, effective-dated ставки, обработку
аванса и окончательной выплаты. Это не меняет scope, но блокирует приёмку
payroll calculation.

### Внешние входные данные

- Владелец предоставляет доступ к сервисному приложению Saby для тестового
  запроса; секреты не фиксируются в документации.
- Владелец предоставляет реальные примеры файлов поставщиков для regression-
  набора.
- Формулы УСН «Доходы» документируются по материалам ФНС и
  принимаются владельцем как управленческий расчёт.

## 4. План реализации

### Этап 0. Зафиксировать контракты

Результат: требования превращены в проверяемые правила.

- Создать ADR по единицам, общему остатку и размещениям.
- Создать ADR по видам выручки и закрытию периодов.
- Составить матрицу `требование → сценарий → API → таблицы → тест`.
- Зафиксировать новые permissions отдельно для склада, поставок, Saby-
  сопоставлений, зарплаты, финансов и налогов.

Критерий выхода: нет открытого решения, меняющего базовые сущности или права.

### Этап 1. Доменный фундамент и миграции

Результат: новая модель доступна через repositories и транзакции, ещё без
массового подключения UI.

- Расширить товар: `productType`, группа, производитель, масса пачки, артикулы,
  штрихкоды и внешние ID.
- Добавить группы с обязательным типом товара и версионируемую историю
  продажных цен.
- Разделить общий остаток и размещения по локациям.
- Разделить складские локации, торговую точку расписания и внешнюю точку Saby.
- Добавить поставки, партии, строки поставок и FIFO allocations.
- Добавить сессии инвентаризации и периоды расхода.
- Добавить внешние Saby-сущности, raw inbox, mappings и sync cursor.
- Добавить расходы, настройки зарплаты и финансовые периоды.
- Усилить ограничения БД: целые пачки/штуки, уникальный штрихкод, одна Saby-
  позиция на один товар, запрет обычного отрицательного остатка.

Критерий выхода: миграции повторяемы; новые инварианты покрыты unit,
repository и concurrency-тестами; production-код не обращается к `AppState`.

### Этап 2. Каталог, локации и базовые складские операции

Результат: продавец может безопасно работать с новым складским контуром.

- Обновить карточки и группы товаров.
- Добавить создание и архивацию локаций администратором.
- Реализовать включение/выключение полок и очередь нераспределённого товара.
- Реализовать приём размещения сканированием и выбором полки.
- Реализовать перемещения между полками без изменения общего остатка.
- Реализовать перенос одной пачки весового товара в зал.
- Реализовать брак с необязательным комментарием.
- Запретить ручное продажное списание штучных товаров.
- Оставить отмену складских операций только администратору.

Критерий выхода: WebApp на мобильном устройстве проводит основные операции;
повтор запроса не создаёт дубль; параллельные операции не дают отрицательный
остаток.

### Этап 3. Поставки, партии, импорт и дубли

Результат: подтверждённая поставка атомарно создаёт партии, товары и остатки.

- Построить pipeline: загрузка → извлечение таблиц → нормализация → mapping →
  классификация → preview → commit.
- Поддержать все листы, скрытые листы, несколько таблиц, формулы, ручное
  выделение таблицы и ручное сопоставление колонок.
- Выполнять распознавание локально, без AI и передачи накладных внешним
  сервисам; импортировать проверенное вычисленное значение формулы.
- Добавить редактирование preview, исключённые строки и шаблоны поставщиков с
  проверкой структуры.
- Добавить управляемый список производителей и их подтверждённые алиасы.
- Добавить классификацию группы с настраиваемым порогом уверенности 80%,
  объяснением результата и блокировкой нерешённых конфликтов.
- Блокировать всю поставку при любой нерешённой строке.
- Хранить hash файла и запрещать повторное применение.
- Создавать партии, цену закупки, доставку и происхождение каждой строки.
- Разрешить подтверждение поставки без закупочной цены, но создать задачу и
  напоминание для её последующего заполнения.
- Реализовать кандидатов дублей, объяснение score, проверенные алиасы,
  обратимый merge и полное provenance.
- Оставлять главной более старую карточку; не объединять разных производителей;
  считать одинаковый штрихкод у разных производителей критическим конфликтом.
- Реализовать откат поставки компенсирующей операцией, включая явно
  подтверждённый отрицательный остаток.

Критерий выхода: набор реальных файлов проходит regression-тесты; commit
атомарен; rollback/merge/undo сохраняют историю и пересчитывают FIFO.

### Этап 4. Инвентаризация и расход весовых товаров

Результат: еженедельный физический пересчёт становится источником фактического
расхода.

- Создавать одну активную инвентаризацию всего склада только для весовых
  товаров.
- Назначать одного заполняющего сотрудника; совместное редактирование не
  поддерживать. День по умолчанию — понедельник.
- На время сессии блокировать складские движения.
- Вводить только целое число пачек без черновика.
- Применять результат продавцом без подтверждения администратора.
- Рассчитывать расход периода по началу, поставкам и физическому остатку.
- Связывать оперативные переносы в зал с итогом периода без двойного расхода.
- Создавать общий расход периода без полки-источника и не менять оперативные
  размещения по полкам.
- Ставить кассовые события, пришедшие во время блокировки, в очередь и применять
  после закрытия по времени чека.
- Добавить напоминания Telegram до завершения инвентаризации.

Критерий выхода: эталонный пример `10 + 5 − 8 = 7` даёт расход 7 независимо от
числа оперативных переносов; повторное закрытие не меняет данные.

### Этап 5. Интеграция Saby и фактическая выручка

Результат: штучные продажи, возвраты и общая выручка поступают автоматически.

- Реализовать server-only OAuth и безопасное хранение секретов.
- Проверять конфигурацию одной организации, одной торговой точки и одной кассы;
  выдавать приложению минимальные права и при возможности ограничение по IP.
- Загружать продажи каждые 15 минут с overlap-окном и пагинацией.
- Выполнять ночную повторную сверку.
- Использовать webhook только как сигнал ускоренного опроса.
- Сделать импорт идемпотентным по устойчивому ключу продажи.
- Учитывать только завершённые фискальные продажи.
- Игнорировать удалённые, отказанные и нефискальные позиции.
- Если ранее применённая продажа позднее стала удалённой, отказанной или
  нефискальной, создавать компенсирующие движения stock и выручки.
- Изменение количества, цены или скидки применять отдельной дельтой, не
  переписывая ранее зафиксированное событие.
- Учитывать скидку по фактической цене; возврат проводить обратным событием.
- Возврат, поднимающий остаток выше принятого количества, сохранять с
  предупреждением, но не отклонять.
- Не менять весовой остаток кассовыми событиями.
- Добавить очередь неизвестных позиций и ручное сопоставление администратором.
- До сопоставления включать сумму неизвестной позиции в общую выручку, но не
  менять товарный остаток.
- Основное соответствие хранить по UUID Saby; штрихкод, артикул и название
  использовать только для предложения. Внешнее название сохранять как алиас и
  не заменять им название Dvorik.
- После сопоставления выполнять детерминированный backfill остатков, продаж и
  финансовых показателей.
- Отправлять сводку ошибок синхронизации и неизвестных позиций.
- После подтверждённой доступности Saby отключить ручной ввод общей дневной
  выручки продавцами.

Критерий выхода: повторная загрузка одного окна не создаёт дублей; поздний
возврат или смена состояния корректирует прежний факт ровно одной компенсацией;
неизвестная позиция не блокирует остальные продажи.

### Этап 6. Признание выручки и аналитика расхода

Результат: фактические и оценочные показатели не смешиваются.

- Реализовать интервальную оценку реализации весовых списаний.
- Реализовать прогноз последнего интервала и замену прогнозного значения
  фактическим.
- Реализовать вопрос бота для первого списания по `DEC-07` с повтором каждые
  три дня без лимита.
- Сохранять историческую цену операции.
- Построить графики: Saby-продажи штучных товаров; инвентаризационный расход
  весовых товаров; пунктирная оперативная оценка незакрытого периода.
- Рассчитать пачки/день, кг/день, рейтинг скорости и ожидаемый запас в днях.

Критерий выхода: отчёт явно различает `actual`, `estimated` и `forecast`; после
инвентаризации пунктирная оценка заменяется итогом, а не суммируется с ним.

### Этап 7. Расписание, кадровые события и зарплата

Результат: текущий календарь расширен без отдельного кадрового приложения.

- Зафиксировать дневные смены 10:00–21:00 и ручное составление графика.
- Сохранить общий календарь и взаимный обмен одной смены без approval
  администратора.
- При обмене каждый участник отдаёт одну смену и получает другую; одиночная
  передача смены не считается обменом.
- Разрешить отмену принятого обмена только администратору.
- Добавить предупреждения пересечений без автоматического запрета.
- Добавить отпуск, больничный, опоздание, невыход и неполную смену.
- Добавить индивидуальный оклад, аванс, основную выплату, норму смен, доплату,
  удержания и оплату отсутствий.
- Не пересчитывать базовый оклад по числу смен; считать только переработку сверх
  общей нормы и отдельные кадровые корректировки. Опоздание оставлять
  информационным.
- Поддержать процентную или фиксированную дневную оплату отпуска и больничного.
- Добавить премии и раздельные переключатели управленческого НДФЛ и взносов.
- Хранить reference-трактовку обычной трудовой премии как облагаемой отдельно от
  management override владельца; внутреннее исключение не должно выглядеть как
  юридическое освобождение.
- До реализации утвердить payroll formula: начисленная или выплачиваемая сумма,
  НДФЛ, взносы, аванс, остаток выплаты и effective-dated ставки.
- Ограничить зарплатные данные решением `DEC-04`.
- Сохранять скрытый технический аудит.

Критерий выхода: календарь доступен сотрудникам; зарплатный расчёт и исходные
настройки доступны только разрешённой роли; обмен не меняет число смен.

Этот этап после этапа 1 можно разрабатывать параллельно этапам 3–6.

### Этап 8. Расходы, налоги и финансовые отчёты

Результат: владелец получает управленческий, а не бухгалтерский отчёт.

- Добавить разовые и регулярные расходы с периодом признания.
- Учесть FIFO-себестоимость, доставку, зарплату, аренду, коммунальные и прочие
  статьи.
- Отображать reference-налоги зарплаты и management overrides раздельно.
- Учитывать доставку партии отдельной статьёй, не распределяя её по товарам.
- Для кофе не учитывать ингредиенты и расходники; применять подтверждённую
  управленческую модель 60% прибыли и 40% условных затрат.
- Пересчитывать открытые периоды после изменения закупочной цены или расхода.
- Изменять закрытый период после поздней закупочной цены только по `DEC-12`.
- Помечать отчёт неполным при незаполненной закупочной цене.
- Реализовать effective-dated правила УСН «Доходы»; остальные режимы оставить
  вне первого релиза.
- Хранить расчётный и фактически уплаченный налог раздельно.
- Автоматически закрывать прошлый месяц 11-го числа; повторное открытие — только
  владельцем.
- Дать уровни отчёта: штучный товар, группа «Сладости», партия и общий период.
- Отдельно показывать выручку, валовую, операционную и чистую прибыль,
  маржинальность и рентабельность.

Критерий выхода: контрольные финансовые сценарии сверены и приняты владельцем
как управленческий расчёт по материалам ФНС; закрытый период не меняется без
явного повторного открытия.

### Этап 9. Доступы, уведомления и UX-приёмка

Результат: каждый пользователь видит только свой рабочий контур.

- Разделить общие отчёты, закупочные данные, зарплаты, налоги и прибыль на
  отдельные backend permissions.
- Оставить продавцу только Telegram WebApp: сканирование, склад, разрешённые
  операции, инвентаризация и календарь.
- Оставить поставки администратору и владельцу; финансы — владельцу.
- Реализовать Telegram-заявку на доступ и немедленный отзыв сессий при
  блокировке.
- Реализовать desktop magic link через Telegram.
- Добавить ежедневную настраиваемую сводку владельца и системные уведомления.
- Дать владельцу настройку состава, времени и часового пояса ежедневной сводки;
  не добавлять уведомление о прогнозном остатке менее N дней.
- Хранить технический аудит бессрочно без пользовательского экспорта.
- Проверить mobile, tablet и desktop, ошибки, empty states, loading, retry,
  конфликты и доступность.

Критерий выхода: отрицательные permission-тесты и ролевые E2E проходят для всех
трёх ролей.

### Этап 10. Production-подготовка и запуск

Результат: полный новый scope готов к работе на `dvorik.shop`.

- Проверить clean install/build/smoke на целевом Linux.
- Проверить миграции на копии production-БД перед каждым релизом.
- Выполнить нагрузочную проверку импорта, Saby sync, инвентаризации и отчётов.
- Настроить постоянные процессы API, Saby scheduler, outbox worker и Telegram.
- Подготовить мониторинг, Telegram-ошибки, health checks и документированный
  runbook восстановления. Из-за `DEC-15` фактическое восстановление и простой
  до одного часа не подтверждены испытанием.
- Настроить принятую владельцем недельную локальную backup-политику и явно
  сохранить принятый риск потери до семи дней данных.
- Проверить выполнение backup job и удаление копий старше месяца без проверки
  восстановления содержимого.
- До отключения legacy вручную завести и сверить пользователей, каталог, цены,
  пачки, barcode, полки, начальные остатки, поставщиков, Saby mappings, график,
  payroll settings, расходы и УСН-конфигурацию.
- Провести сценарную проверку продавцами.
- Получить финальное решение владельца о релизе.
- Запустить новую систему без переноса legacy-данных и отключить legacy после
  успешного smoke.

Критерий выхода: release gate зелёный, миграционный rollback отрепетирован на
disposable копии, начальные операционные данные подписаны владельцем, backup job
и retention работают, владелец подтвердил готовность, все процессы наблюдаемы.

## 5. Зависимости и приоритет

| --- | --- | --- |

| DATA — доменная модель и миграции | P0 | FND |
| STOCK — каталог, остаток и размещение | P0 | DATA |

Технический пилот можно начать после `FND`, `DATA`, `STOCK`, `SUPPLY`, `INV`,

документу. Полный production-релиз включает также `REVENUE`, `PEOPLE` и `FIN`,
если владелец отдельно не сократит scope.

## 6. Стратегия проверки

### На каждом этапе

- unit-тесты доменных формул и state transitions;
- repository и migration tests;
- API contract tests: success, forbidden, conflict, retry и idempotency;
- concurrency tests для остатков, инвентаризации, merge и sync;
- audit/outbox проверяются в той же транзакции;
- UI проверяется на 390 px, tablet и desktop;
- документация и acceptance-матрица обновляются вместе с кодом.

### Обязательные сквозные сценарии

1. Поставка весового товара → размещение → перенос пачки в зал →
   инвентаризация → закрытый расход → финансовый отчёт.
2. Поставка штучного товара → Saby-продажа со скидкой → возврат → FIFO →
   фактическая прибыль.
3. Неизвестная позиция Saby → общая выручка → ручное сопоставление → backfill.
4. Merge после поставок и продаж → новые операции → undo с сохранением
   происхождения.
5. Откат поставки после расхода → подтверждённый отрицательный остаток →
   предупреждение → ручное восстановление.
6. Активная инвентаризация → заблокированное движение → queued Saby sale →
   применение после закрытия по времени чека.
7. Обмен сменами → кадровое событие → зарплатный расчёт → проверка доступа.
8. Закрытие месяца → попытка позднего изменения → повторное открытие владельцем.
9. Потеря процесса worker → повторный запуск без потери и дублей событий.
10. Миграция на копии БД → smoke → rollback → повторная миграция.

## 7. Release-gates

Production-запуск запрещён, пока не выполнены все условия:

- закрыты решения, влияющие на выпущенный scope;
- подтверждена доступность Saby API на реальном тарифе;
- реальные файлы поставщиков входят в regression-набор;
- нет production-обращений к legacy `AppState`;
- пройдены миграция и rollback на копии production-БД;
- пройдены ролевые E2E и сквозные сценарии;
- задокументирован runbook восстановления; отсутствие проверки restore и
  неподтверждённый RTO явно приняты владельцем;
- продавцы завершили проверку основных операций;
- владелец принял финансовые расчёты и дал решение о запуске.

## 8. Первый исполняемый инкремент

После утверждения этого плана начинать не с интерфейсов, а с пакета
`FND + DATA`:

1. оформить ADR общего остатка, размещений, пачек и финансовых фактов;
2. обновить permissions;
3. подготовить миграции групп, типов товаров, массы пачки, истории цен,
   поставок/партий и размещений;
4. добавить новые repositories и инвариантные тесты;
5. реализовать один контрольный вертикальный сценарий: поставка весовой пачки →
   размещение → перенос одной пачки в зал.

После его приёмки можно параллельно запускать `SUPPLY`, `SABY` и `PEOPLE`, не
нарушая общую модель данных.

## 9. Definition of Done для пакета

Пакет завершён, только если:

- его требования имеют acceptance-сценарии;
- права проверяются backend-ом;
- изменения проходят через application service и одну транзакцию;
- ошибки имеют стабильные коды;
- повтор команды безопасен;
- есть audit и необходимые уведомления;
- пройдены negative-path и concurrency-тесты;
- UI показывает loading, empty, error, conflict и success;
- миграция и rollback проверены;
- документация отражает фактическое состояние.
