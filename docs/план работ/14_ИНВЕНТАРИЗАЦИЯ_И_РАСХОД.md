# B05. Инвентаризация и расход весовых товаров

## Результат блока

Еженедельный общий пересчёт весовых товаров закрывает период и создаёт
фактический расход без двойного учёта оперативных переносов.

## Границы

Включены inventory session, блокировка движений, физический остаток в пачках,
закрытие расхода, связь с оперативными переносами, очередь внешних событий и
первичное признание расчётной выручки. Штучные товары не пересчитываются.

## Цели

1. Сделать инвентаризацию источником фактического расхода.
2. Исключить двойное списание после закрытия периода.
3. Не требовать распределения расхода по полкам.
4. Корректно обработать конкурирующие движения и Saby events.
5. Разделить actual, estimated и forecast.

## План работ

### 1. Inventory session

- Одна активная сессия всего склада.
- Только весовые товары.
- Один заполняющий сотрудник без совместного редактирования.
- День по умолчанию — понедельник.
- Снимок начального остатка, поставок и версий.
- Черновик после выхода не сохраняется.

### 2. Блокировка

- На время сессии запретить складские mutations.
- Повторный запуск второй сессии отклонять.
- Saby events принимать в durable inbox, но не применять к stock до закрытия.
- После завершения применять queued events по времени чека.
- Зависшую сессию разрешать завершить или отменить по явной процедуре.

### 3. Ввод и закрытие

- Ввод только целых пачек.
- Не показывать предупреждение о «слишком большой» разнице.
- Продавец применяет результат без approval администратора.
- Комментарий необязателен.
- Формула: начало + поставки − физический остаток.
- Расход создаётся без полки-источника и не меняет placement projection.

### 4. Связь с оперативными переносами

- Переносы в зал остаются временной детализацией текущего периода.
- При закрытии они связываются с consumption period.
- Итоговый расход не складывается с переносами повторно.
- После закрытия отчёты используют физический итог, сохраняя историю оценок.

### 5. Признание весовой выручки

- Историческая цена фиксируется в момент переноса.
- Следующий перенос задаёт фактический интервал реализации предыдущего.
- Последний интервал прогнозируется по предыдущему.
- Для первого переноса бот спрашивает через три дня.
- «Закончилось» признаёт реализацию в момент ответа.
- «Не закончилось» и отсутствие ответа повторяют вопрос каждые три дня без
  лимита; первый ответ на конкретный вопрос окончателен.
- Сезонная модель не применяется.

### 6. Напоминания и наблюдаемость

- Telegram напоминает сотрудникам до завершения.
- Ошибка закрытия видна администратору, но не оставляет частичный результат.
- Метрики: активная сессия, длительность, queued events, ошибка закрытия.

- consumption-period ledger;
- scheduled Telegram notifications через outbox;
- domain/concurrency/timezone tests;
- seller mobile UI.

## Критерии приёмки

- Вторая инвентаризация не стартует, пока активна первая.
- Любое складское движение во время сессии отклоняется без изменения данных.
- Saby event во время сессии не теряется и применяется после закрытия по времени
  чека.
- Ввести дробную пачку нельзя.
- Инвентаризацию заполняет и закрывает один продавец.
- Пример `10 + 5 − 8` создаёт расход 7 при любом числе оперативных переносов.
- Закрытие не требует выбора полки и не изменяет размещения.
- Повтор submit не создаёт второй расход.
- Ошибка закрытия оставляет сессию и остатки в согласованном состоянии.
- Actual, estimated и forecast доступны как разные типы данных.
- Вопрос бота повторяется без лимита согласно решению владельца.
