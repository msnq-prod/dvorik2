# План доработок Dvorik

## 1. Цель

Оставить `gpt-version` единственной актуальной системой и перенести в неё лучшие функции `recovered-dvorik` без копирования legacy-архитектуры.

Итоговая система должна иметь:

- один домен и одну базу данных для WebApp, админки, Telegram-бота и фоновых задач;
- современную current-админку с операционным dashboard legacy;
- единый календарь смен в WebApp и Telegram;
- безопасные складские операции, импорт, отчёты, уведомления и восстановление данных.

## 2. Обязательные принципы

1. `gpt-version` — единственный source of truth.
2. Legacy остаётся только источником бизнес-правил и UX-референсом.
3. Telegram не обращается к БД напрямую: только к общим application services.
4. Все изменения остатков, смен, импортов, ролей и объединений проходят через permissions, audit и idempotency.
5. Любая массовая операция сначала имеет preview, затем commit и понятный rollback/undo.
6. Публичные current API сохраняются либо мигрируют через совместимый переходный слой.

## Этап 0. Зафиксировать решения

### Работы

- Зафиксировать `gpt-version` как актуальный продукт, `recovered-dvorik` как read-only reference.
- Выбрать production persistence:
  - рекомендуемый первый шаг — нормализованный SQLite с миграциями и repository layer;
  - переход на PostgreSQL оставить возможным без изменения application services.
- Решить модель смен:
  - смена на весь день или с реальным временем;
  - закрытый день общий или по отдельной локации;
  - один или несколько сотрудников на одной точке;
  - видит ли продавец весь график команды.
- Утвердить Telegram runtime: webhook в current Node API + отдельный outbox worker.
- Зафиксировать timezone `Asia/Vladivostok` во всех датах, сменах и фоновых задачах.

### Артефакты

- `docs/PROJECT_STATE.md`;
- ADR по БД;
- ADR по Telegram/outbox;
- спецификация состояний смены и заявки на подмену.

### Приёмка

- Нет открытых решений, меняющих схему данных или API следующих этапов.
- В документации явно разделены implemented, target и legacy-reference.

## Этап 1. Стабилизировать current и вернуть операционную главную

### 1.1 Календарные дефекты

- Проверять конфликт смен у получателя при принятии подмены.
- Запретить подмену на заблокированного/неактивного сотрудника.
- Убрать из UI чужие смены как fallback, когда у пользователя нет своих смен.
- Либо реализовать реальное время смен, либо удалить ложные `start/end` из формы и контракта.
- Добавить тесты на повторную, отменённую, просроченную и конфликтующую подмену.

### 1.2 Dashboard

- Подключить существующий `DashboardPage` вместо дублирующего меню.
- Оставить быстрые действия первым блоком.
- Добавить:
  - кто сегодня на смене;
  - низкие и нулевые остатки;
  - остатки по ключевым локациям;
  - последние движения;
  - непрочитанные уведомления;
  - ошибки/операции, требующие внимания.

### Приёмка

- Admin после входа видит состояние магазина, а не второй список разделов.
- Seller видит только разрешённые быстрые действия и свой график.
- Все schedule negative-path tests проходят.
- `npm run check` и `npm run test` проходят.

## Этап 2. Нормализовать хранение данных

### 2.1 Таблицы

- `users`, `roles`, `permissions`, `sessions`;
- `products`, `product_identifiers`, `suppliers`, `supplier_skus`, `product_aliases`;
- `locations`, `stock_balances`, `stock_operations`;
- `shifts`, `shift_assignments`, `shift_swap_requests`, `schedule_days`, `rotation_templates`;
- `imports`, `import_rows`, `merge_jobs`, `label_jobs`;
- `notification_preferences`, `outbox_messages`;
- `audit_entries`, `schema_migrations`.

### 2.2 Repository layer

- Убрать прямую работу domain services с глобальным `AppState`.
- Разделить transaction boundary и application service.
- Сохранить current IDs и API-формат на переходный период.
- Добавить optimistic version или транзакционную блокировку для остатков и смен.

### 2.3 Миграция

- Конвертер из `app_state.payload` в новые таблицы.
- Dry-run с отчётом количества сущностей и конфликтов.
- Автоматический backup до миграции.
- Проверка инвариантов после миграции.
- Rollback на исходную копию БД.

### Приёмка

- Повторный запуск миграции безопасен.
- Суммарные остатки, операции, смены, пользователи и задания печати совпадают до/после миграции.
- Две параллельные складские операции не теряют изменения.
- Audit больше не переписывает весь state целиком.

## Этап 3. Объединить календарь и расписание

### 3.1 Домен

- Добавить рабочие/закрытые дни.
- Добавить day detail: сотрудники, точка, статус, комментарий.
- Добавить rotation template без жёсткого ограничения на 3/4 сотрудников.
- Генерация графика только через preview:
  - создаваемые смены;
  - конфликты;
  - изменения существующих смен;
  - пропущенные закрытые дни.
- Commit генерации — одной транзакцией и с audit.
- Добавить массовую будущую замену сотрудника с preview.
- Добавить экспорт месяца/двух месяцев в PDF/CSV.

### 3.2 WebApp

- Сохранить current 42-cell month grid.
- По клику на дату открывать drawer/panel дня.
- Показывать рабочие, свободные, закрытый день, точку и заявки на подмену.
- Добавить фильтр сотрудника и точки.
- Добавить явные статусы подмен: pending/accepted/declined/cancelled/expired.

### Тесты

- Месяцы с 4, 5 и 6 календарными строками.
- Переход декабря/января и leap year.
- Конфликт сотрудника и точки.
- Закрытый день.
- Preview не меняет данные.
- Commit атомарен.
- Повторный commit идемпотентен.

### Приёмка

- Администратор создаёт график на месяц без ручного назначения каждой даты.
- Сотрудник видит корректный график и может безопасно запросить подмену.
- Генерация никогда молча не удаляет ручные назначения.

## Этап 4. Telegram-бот, onboarding и уведомления

### 4.1 Telegram adapter

- Webhook endpoint с проверкой секрета Telegram.
- Дедупликация `update_id`.
- Команды и меню:
  - `/start`;
  - «Мой график»;
  - «Наличие»;
  - «Поиск товара»;
  - «Уведомления».
- Inline-календарь на 42 ячейки:
  - `✅` моя смена;
  - `✖` закрытый день;
  - переход между месяцами;
  - day detail;
  - подмена Accept/Decline/Preview.

### 4.2 Onboarding

- Новый Telegram user создаётся со статусом `pending`.
- Бот собирает имя/фамилию.
- Super admin получает запрос с ролями seller/admin и кнопками approve/reject.
- Одобрение активирует пользователя и отзывает старые невалидные сессии.

### 4.3 Outbox и уведомления

- Все Telegram/WebApp сообщения сначала пишутся в `outbox_messages`.
- Worker поддерживает retry, backoff, sent/failed и ручной повтор.
- Настройки пользователя:
  - `off`;
  - `instant`;
  - `daily`.
- События:
  - нулевой остаток;
  - последняя единица/порог;
  - поступление;
  - новая/принятая/отклонённая подмена;
  - изменение графика.
- Daily digest по `Asia/Vladivostok`.

### Приёмка

- WebApp и бот показывают одинаковый график из одной БД.
- Повторный webhook не дублирует действие.
- Ошибка Telegram не теряет событие и видна администратору.
- Неактивный пользователь не получает доступ к данным.

## Этап 5. Импорт, отчёты и жизненный цикл товаров

### 5.1 Импорт

- Перенести в current:
  - supplier/invoice metadata;
  - определение листа и строки заголовка;
  - ручное сопоставление article/name/quantity;
  - разбор количества с текстом и единицами;
  - supplier-specific SKU;
  - warnings и rejected rows.
- Сохранить current:
  - preview;
  - hash duplicate guard;
  - idempotent commit;
  - conflict-aware undo;
  - audit.
- Собрать regression fixtures из legacy tests и реальных файлов поставщиков.

### 5.2 Отчёты

- Страница и API отчётов:
  - низкий остаток;
  - нулевой остаток;
  - остаток в диапазоне;
  - все товары;
  - архив;
  - движения за период;
  - расхождения инвентаризации.
- CSV/PDF export и отправка выбранного отчёта в Telegram.

### 5.3 Архивация

- Scheduled archive sweep только для нулевых товаров без пополнения N дней.
- Dry-run, audit, список кандидатов и восстановление товара при новом поступлении.

### Приёмка

- Контрольные legacy-файлы дают ожидаемые строки и количества.
- Повторный импорт не удваивает остаток.
- Откат запрещён после зависимых движений.
- Автоархив не затрагивает товар с остатком или свежим поступлением.

## Этап 6. Поиск, дубли и фотографии

### 6.1 Поиск

- Серверный поиск по названию, локальному имени, артикулу, barcode и aliases.
- FTS с fallback.
- Единый endpoint для WebApp и Telegram inline search.

### 6.2 Дубли

- Автоматические candidate groups.
- Нормализация `ё/е`, пунктуации и служебных фраз.
- Match score и explanation.
- Field-level resolution для имени, производителя, фото, identifiers и остатков.
- Сохранить current snapshot/commit/undo/audit.

### 6.3 Медиа

- Upload endpoint с типом/размером файла.
- Сжатие и генерация безопасного имени.
- Локальное/object storage через общий интерфейс.
- Удаление только после проверки ссылок и backup policy.

### Приёмка

- Поиск одинаково работает в WebApp и боте.
- Merge preview полностью показывает последствия.
- Undo восстанавливает обе карточки, identifiers и остатки.
- Битое или слишком большое изображение не сохраняется.

### Работы

- Общий work buffer выбранных товаров.
- Добавление из поиска или списка локации.
- Последовательные transfer/write-off/inventory actions без повторного поиска.
- Сохранение черновика локально, но commit только через API.
- Подключить current dark theme к graphite-направлению legacy.
- Добавить `comfortable/dense` mode.
- Проверить desktop, tablet и mobile.
- Accessibility: contrast, focus, keyboard, labels, status announcements, touch targets.

### Приёмка

- Основные операции выполняются на планшете без горизонтального скролла.
- Любое изменение остатков остаётся отдельной audited operation.
- Dense mode не уменьшает touch targets ниже принятого размера.

## Этап 8. Миграция и запуск

### Подготовка

- Backup production data.
- Репетиция миграции на копии.
- Сверка количества сущностей и контрольных остатков.
- Smoke/E2E для admin, seller, Telegram и фоновых задач.
- Проверка восстановления backup.

### Cutover

1. Остановить legacy writes.
2. Создать финальный backup.
3. Выполнить миграцию.
4. Запустить current API, worker и Telegram webhook.
5. Выполнить smoke-проверку.
6. Оставить legacy read-only на ограниченный период.

### Rollback

- Остановить current writes.
- Восстановить предмиграционный backup.
- Вернуть Telegram webhook/entrypoint на предыдущую версию.
- Сохранить логи неудачной миграции отдельно.

### Приёмка

- Нет расхождений в остатках и пользователях.
- Нет потерянных/дублированных Telegram updates.
- Все P0/P1 сценарии проходят на production-like данных.
- Legacy больше не принимает изменения после подтверждённого cutover.

## 5. Рекомендуемый первый инкремент

Первый инкремент должен включать только:

1. `FND-01` — решения и ADR;
2. `FIX-01` — исправление конфликтов подмен и контракта времени;
3. `UI-01` — подключение операционного dashboard;
4. проектирование `DB-01` без миграции production data.

После этого можно начинать нормализацию БД и календарный домен без риска закрепить неправильные контракты.

## 6. Что не входит в первый цикл

- перенос legacy Python-кода;
- production cutover;
- полный визуальный редизайн всех страниц;
- планшетный буфер;
- автоматический fuzzy merge без preview;
- Telegram-бот, пока не зафиксирован единый календарный домен и persistence.
